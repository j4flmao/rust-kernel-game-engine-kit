# 3D GPU Rendering Plan

Status: **implementation in progress — bounded native world-pass baseline is now implemented**

This document records the work required to finish the Rubik's Cube example.
The current implementation has completed the bounded renderer contracts, native
resource staging, shader compilation, and a Windows/Linux Vulkan world-pass
bring-up. Depth resources already exist. General indexed mesh submission, GPU culling, and production fallback
gates remain explicit follow-up phases below. It intentionally separates a real
GPU 3D path from the existing UI renderer and from the CPU/headless validation
path.

## 1. Current audit

The repository already contains the data contracts needed to start a 3D renderer:

- typed `RenderTransform` and `RenderMaterial` ECS components;
- bounded, frame-owned `RenderWorld` extraction;
- deterministic CPU `CpuRenderManifest` mesh/material batching;
- bounded `GpuFramePreparation` instance records and indirect command records;
- checked upload-size arithmetic and Vulkan indirect-command encoding;
- a `RenderBackend` abstraction and a headless validating backend;
- platform Vulkan loader, swapchain, present, and UI graphics-pipeline code.

The repository has a native world-pass baseline. The phases below are design checkpoints, not a list of wholly absent modules.

| Capability | Current implementation | Remaining evidence |
| --- | --- | --- |
| Resource tables | `renderer_3d.rs` mesh/material handles | General native mesh submission |
| World pipeline and depth | `platform/windows/present.rs`: world pipeline, depth image/view | Native resize, image correctness and recovery |
| Camera and layer animation | Rubik camera, driver and scene modules | Interactive regression validation |
| Shader compilation | `shaders/` and build pipeline | Hardware-specific runtime correctness |
| GPU compute culling/binning | Design target | Implementation and CPU/GPU differential tests |

Rubik's bring-up shader generates cube vertices from the vertex index. Its mesh-table contract does not establish arbitrary indexed mesh rendering. Backend source existence does not establish Windows/Linux validation parity. See [rendering](rendering.md) for the current CPU preparation boundary.

Therefore the Rubik example must not be added as a UI illusion or presented as
GPU rendering before these phases are complete.

## 2. Target frame architecture

```text
Simulation ECS
    |
    | bounded extraction; no ECS pointers cross the boundary
    v
RenderWorld
    |
    | stable handles, transforms, bounds, visibility, mesh/material IDs
    v
Frame preparation
    |
    +--> CPU manifest and fallback draw batches
    |
    +--> bounded upload ranges
             |
             +--> transfer: mesh/material/instance uploads
             |
             +--> compute: frustum culling and mesh/material binning
             |        |
             |        +--> visible IDs, bounded counters, indirect commands
             |
             +--> graphics: depth-tested indexed/indirect world pass
                      |
                      +--> UI/overlay pass
                               |
                               +--> present
```

The world pass and UI pass remain separate. UI ordering, clipping, and text must
not be forced through the opaque world mesh path.

## 3. Implementation phases

### 3D-0 — Contract and feature gate

Freeze the backend-neutral contracts before adding Vulkan calls:

- `MeshHandle`, `MaterialHandle`, `TextureHandle`, and `ViewHandle` use
  generation-checked IDs;
- `MeshAsset` contains bounded vertex/index metadata and validated ranges;
- `RenderView` contains checked view/projection matrices, viewport, and culling
  planes;
- `WorldPass` describes color/depth targets and opaque/transparent policy;
- `RenderFrame` owns all data submitted to the backend for one frame;
- `gpu_3d` is explicit and opt-in until native validation is green;
- CPU/headless mode remains the default and produces the same logical draw plan.

Acceptance:

- no raw Vulkan handles appear in ECS, gameplay, or example-facing types;
- all counts, strides, and byte sizes use checked arithmetic;
- invalid handles and stale generations are rejected deterministically;
- capacity exhaustion returns a typed error without changing prior state.

### 3D-1 — Mesh and material resource tables

Add renderer-owned, bounded tables for:

1. immutable vertex data;
2. immutable index data;
3. mesh ranges and bounds;
4. material parameters;
5. optional texture/sampler references;
6. per-frame upload generations.

The first supported vertex format should be deliberately small and explicit:

```text
position: float3
normal:   packed or float3
uv:       float2
color:    packed RGBA8 or material-only
```

Do not expose arbitrary runtime-controlled strides or offsets. Validate alignment,
index type, range containment, and maximum asset sizes before storing an asset.

### 3D-2 — Vulkan resource ownership and staging

Implement renderer-owned RAII resources on both native platforms:

- device-local vertex and index buffers;
- host-visible staging buffers;
- bounded frame upload rings;
- material and instance buffers;
- explicit transfer barriers;
- deferred destruction tied to frame-fence completion.

The allocator path must distinguish allocation failure, unsupported memory type,
device loss, and invalid resource state. No upload may use a pointer after the
source frame or staging allocation has been released.

### 3D-3 — Real 3D graphics pipeline

Add a world render pass with:

- color attachment compatible with the swapchain;
- depth attachment with a selected depth format;
- depth-test/depth-write enabled for opaque geometry;
- back-face culling and a documented winding convention;
- vertex input matching the stable mesh format;
- descriptor or push-constant layout for camera and material data;
- a vertex shader applying model/view/projection transforms;
- a fragment shader reading material data;
- explicit pipeline lifetime and swapchain recreation.

The UI pipeline remains separate. The world pass must not reuse the UI shader
layout just because both ultimately present to the same swapchain image.

### 3D-4 — Direct indexed draw correctness path

Before GPU compute culling, make one correct direct/CPU-driven path:

1. prepare the same `CpuRenderManifest` used by headless mode;
2. resolve mesh/material handles to validated GPU resources;
3. bind the world pipeline, vertex buffer, and index buffer;
4. bind camera/material state;
5. record bounded indexed draws per legal batch;
6. execute the UI pass after the world pass;
7. present with the existing synchronization state machine.

Required differential tests compare the CPU manifest with the native command plan.
This phase gives the Rubik example a reliable GPU baseline before indirect work.

### 3D-5 — GPU-driven batching and culling

Only after direct indexed rendering is stable:

- upload changed instance ranges;
- clear bounded visibility and bin counters;
- dispatch conservative frustum culling;
- write visible instance IDs and bounded mesh/material bins;
- generate indirect indexed commands;
- insert compute-to-draw barriers;
- use indirect draws when the negotiated device supports them;
- fall back to the direct path for small scenes or unsupported features.

`draw_indirect_count` and subgroup operations are optional. The first GPU path
must work without assuming them.

### 3D-6 — Camera, resize, and presentation integration

Define one coordinate convention and test it:

- right-handed world space;
- +Y up;
- camera looks along the documented forward axis;
- depth range and front-face winding documented for Vulkan;
- aspect ratio derived from the actual drawable extent;
- near/far planes validated and clamped.

Resize, minimize, swapchain invalidation, device loss, and unsupported depth
formats must return to an explicit renderer state. They must never leave a stale
depth view, framebuffer, descriptor, or command buffer reachable.

### 3D-7 — Rubik's Cube example

Add the example only after 3D-4 is working:

```text
examples/
  rubik_3d.rs
  rubik_3d/
    scene.rs       // 27 cubies, transforms, face/material assignment
    camera.rs      // orbit camera and checked projection
    input.rs       // close/orbit/turn commands
    assets.rs      // bounded cube meshes and material table
    render.rs      // kernel render-frame submission, no Vulkan handles
```

The scene should contain 27 cubie instances and multiple material/mesh batches so
it exercises extraction, sorting, upload ranges, and indirect command generation.
It should render through the kernel's world pass, not through UI rectangles. A
CPU/headless mode should remain available for CI and produce a machine-readable
manifest summary.

Suggested controls:

- mouse drag or arrows: orbit camera;
- `R`: reset camera;
- `X`, `Y`, `Z`: rotate a selected layer;
- `Esc`: close;
- `F3`: show instance/batch/GPU-path diagnostics.

### 3D-8 — Verification and production gates

Add tests for:

- mesh/index range validation;
- stale resource handles and generation reuse;
- zero and maximum capacities;
- checked byte-size overflow;
- camera matrix and frustum edge cases;
- deterministic CPU manifest ordering;
- direct versus indirect draw-plan equivalence;
- depth-format and feature fallback;
- resize and device-loss resource retirement;
- Rubik 27-instance extraction and batch counts.

Add platform jobs for:

- headless Linux and Windows contract tests;
- native Windows Vulkan world-pass smoke;
- native Linux Vulkan world-pass smoke;
- validation layers when available;
- ASan/UBSan/Miri where applicable;
- a bounded multi-minute 3D soak test;
- benchmark regression for extraction, upload bytes, CPU draw planning,
  culling work, and frame latency.

## 4. Security and stability invariants

- Runtime input cannot choose an arbitrary GPU byte offset.
- Every GPU-visible table has a hard element and byte budget.
- Every multiplication and range addition is checked before allocation or copy.
- GPU-written counts are validated before indirect draw consumption.
- Frame-owned resources live until their fence or timeline completion.
- Device loss and allocation failure produce a controlled fallback or typed error.
- Native handles stay inside platform/backend modules.
- The CPU/headless path remains usable without a display or physical GPU.
- The Rubik example cannot make native Vulkan mandatory for repository tests.

## 5. Definition of done

The 3D track is complete only when:

1. Rubik renders actual indexed 3D geometry through a native Vulkan world pass.
2. Depth testing visibly resolves overlapping cubies correctly.
3. The same scene produces equivalent CPU and GPU draw manifests.
4. GPU batching is bounded, measurable, and has a working CPU fallback.
5. Windows and native Linux paths have evidence artifacts, not just compilation.
6. Resize, minimized windows, device loss, and unsupported features are safe.
7. `cargo run --example rubik_3d --release` is documented and playable.
8. Each completion claim links to the corresponding contract test and native validation evidence.
